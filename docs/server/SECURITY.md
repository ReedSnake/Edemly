# Server Security

This document summarizes the current server-side security boundaries.

It is not a complete production security audit. Its purpose is to make the current behavior explicit so API, realtime, file, payment, and tenant changes do not accidentally weaken access control.

## Overview

The server uses JWT Bearer authentication for protected HTTP endpoints and SignalR hubs.

Controllers and hubs should treat authentication as only the first boundary. Operations that touch user-owned or chat-owned data must also verify ownership, chat membership, role, or tenant scope in the application layer.

The current safety model is:

* protected endpoints require a valid JWT;
* controllers resolve the current user id from token claims before calling services;
* chat and message reads require chat membership;
* chat update operations require a chat-level role that can update the chat;
* payment history and payment status checks are scoped to the current user;
* uploaded file reads require authentication through API/proxy paths;
* multi-step writes use transactions where partial state would be user-visible.

## Authentication Boundary

JWT tokens are generated by `JwtService`. The generated token includes:

| Claim | Purpose |
| ----- | ------- |
| `sub` | Authenticated user id |
| `userId` | Authenticated user id used by most controllers and hub code |
| `unique_name` | Username |
| `email` | Email address |
| `jti` | Token id |
| `ClaimTypes.Role` | `User` or `Admin` |

`ApiControllerBase.RequireCurrentUserId` resolves the authenticated user id from configured claim names. Most controllers use `userId`. Payment endpoints also check `ClaimTypes.NameIdentifier`, `userId`, and `sub` for compatibility with payment callback/status flows.

SignalR accepts JWTs from the `access_token` query parameter for hub connections. The hub user id provider resolves `ClaimTypes.NameIdentifier`, `userId`, or `sub`, but current hub method code still expects `userId` to be present.

## Authorization Rules

Authorization rules belong close to the application operation, not only on controller attributes.

Current important rules:

| Area | Rule |
| ---- | ---- |
| Current user profile | `api/users/me` endpoints use the authenticated user id from the token. |
| Public user profile | `api/users/{userId}` is currently public. Treat this as intentional only if public profiles are desired. |
| Chats | chat list and chat detail are scoped to chats where the current user is a member. |
| Chat updates | chat name, description, and icon updates require the current user to have an allowed chat role. |
| Chat members | member lookup by id requires the current user to belong to the same chat. |
| Messages | message history, last-message lookup, and message lookup require chat access. |
| Message writes | send/edit/delete check sender, membership, or chat role depending on the operation. |
| Notes | contact notes are scoped to the current user as creator. |
| Remindings | reminder operations use the current user id. |
| Payments | history is scoped to the current user; status checks reject order ids that do not belong to the current user. |
| Company admin | company create and company email management require the `Admin` role; company list is still public. |

## Realtime Access

`MainHub` and `CallHub` are protected with `[Authorize]`.

`MainHub` handles chat messages, chat notifications, profile notifications, presence, and reminder confirmation. Message send/update/delete methods check chat membership and sender or chat role before writing or broadcasting.

`CallHub` delegates call state and participant checks to `CallService`. Call operations verify that the current user belongs to the relevant chat or call before changing call state or broadcasting call events.

Realtime event names and method names are part of the client contract. Security fixes should preserve names unless the client is updated in the same planned change.

## File Access

File storage is handled through `IFileStorageService` and `FileStorageService`.

Current file access boundaries:

* `api/files`, `api/files/download`, and direct `/uploads/...` controller paths require authentication.
* `EnsureUploadsAuthMiddleware` runs before `UseStaticFiles()` and blocks unauthenticated `/uploads` paths.
* `FileStorageService` prevents global context access to tenant-prefixed files when the first path segment matches a known company.
* Profile picture and chat icon uploads validate image extensions.
* Generic file upload does not currently enforce a strict extension allowlist.

There is not yet a database-backed file ownership or attachment ACL model. An authenticated user with a valid stored file URL may be able to request global uploaded files unless a higher-level feature restricts the URL itself.

## Payment Safety

Payment initiation, history, and status endpoints require authentication.

`api/Payment/return` is public because the payment provider posts back to it. It must not trust a user id supplied by the client. The current completion path finds the payment by transaction/order reference and upgrades the user attached to that payment record through `PaymentService.MarkPaidAndUpgradeUserAsync`.

Payment completion updates the payment status and user subscription in one transaction.

Important current limitation: `WayForPayService.CheckPaymentStatusAsync` is still a stub-like implementation that returns paid. This is acceptable only for local/test mode. Production payment verification must validate the provider response or signature before marking a payment as paid.

## Consistency Boundaries

The server currently uses explicit transaction boundaries for operations where partial persistence would be visible:

* authentication registration creates the user, login info, session, and welcome chat membership in one execution-strategy transaction;
* HTTP message creation commits the message and chat last-message snapshot together;
* hub message creation commits the message and chat last-message snapshot together;
* paid payment completion commits payment status and subscription upgrade together.

Not every write is transactional. Smaller single-entity updates still rely on normal EF Core `SaveChangesAsync` behavior.

## Current Gaps

Review these before production hardening:

* Add tests for chat/message authorization, cache invalidation, snapshots, payment ownership, and file access.
* Replace the WayForPay status stub with real provider verification.
* Decide whether public user profiles and public company listing are intentional.
* Add a file ownership or attachment ACL model if uploaded URLs should not be accessible to every authenticated user.
* Review generic file validation, content scanning, quotas, retention, and orphan cleanup.
* Move in-process presence, verification code state, and cache invalidation to distributed infrastructure before running multiple backend instances.
* Keep real secrets out of committed configuration.
